Why Autback

Your tools already know how to do the work.

The missing piece is a durable, authenticated path from a developer laptop or GitHub Actions to compute you own.

01

Keep the laptop responsive

Send CPU-heavy tests, browser suites, and container builds to a persistent worker while local tools stay usable.

02

Pay for the machine

Use one right-sized VPS across the team instead of metered build minutes. Hetzner is the current host, not a dependency.

03

Keep the exit doors open

Source uses REAPI CAS, environments use OCI images, and builds remain ordinary native Buildx and BuildKit.

Architecture

Repository contract

Three decisions. No pipeline language.

  1. 1

    Link the repository

    A tiny committed file identifies the server-side project. It contains no commands, credentials, hooks, or environment values.

    { "project": "acme-api" }
  2. 2

    Choose an OCI environment

    Build a normal Dockerfile, capture the immutable digest, and activate it for the project.

    autback image build \
  --tag ghcr.io/acme/ci:autback \
  --file Dockerfile.autback
  3. 3

    Run the command you already own

    Keep sequencing and parallelism in Task, Make, your test runner, or a script checked into the repository.

    autback exec \
  --cache go-build=/root/.cache/go-build \
  -- task test

Capacity model

One queue. One worker. The whole machine.

Every dispatcher can submit work. Autback starts it in strict arrival order and admits one operation at a time, so unrelated jobs do not turn a small worker into an oversubscribed scheduler.

Need concurrency? Submit one command whose repository-owned task graph runs work in parallel. The active job can use the worker’s available CPU and memory without Autback inventing resource profiles.
